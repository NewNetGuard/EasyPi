# План автоматической приёмки EasyPi

## Цель

Одна команда должна проверять заявленные функции EasyPi и сохранять доказательства:
результат каждой проверки, HTTP-ответы, состояние служб, ошибки браузера,
скриншоты и trace при сбоях. Повторный запуск должен расходовать главным образом
машинное время, а разбор человеком или агентом требуется только для новых ошибок.

## Стенды

1. **Локальная рабочая копия** — анализ исходников, security-тесты, тесты агента,
   lint, сборка frontend и Go-тесты.
2. **Работающий EasyPi** — только чтение: health, авторизация, состояние служб и
   открытие страниц. Такой прогон не меняет сеть и данные.
3. **Отдельный чистый Pi** — установка, первичная настройка, обновление,
   восстановление, перезагрузка, удаление и искусственные сбои. Устройство должно
   быть предназначено для очистки и повторной установки.
4. **Тестовый VPS и клиенты** — Chameleon, WireGuard, смена сети, повторное
   подключение, DNS/IPv6 leaks, потери пакетов и устойчивость к блокировкам.
5. **Тестовые внешние интеграции** — камеры, Telegram, облачные хранилища и
   Tailscale. Они не должны использовать личные данные и production-аккаунты.

## Этапы

### 1. Общий запуск и инвентаризация — готово

- машинный каталог функциональных областей;
- автоматическая инвентаризация UI-маршрутов и API-обработчиков;
- профили `quick`, `full`, `live-readonly` и `browser`;
- JSON- и Markdown-отчёты в `.build/acceptance/`;
- запрет передачи SSH-паролей через аргументы командной строки.

### 2. Браузерная приёмка — готово

- публичная форма входа и защита закрытых маршрутов автоматизированы;
- подготовлен вход тестового администратора, включая TOTP;
- автоматизирован обход 25 основных страниц после входа;
- автоматизированы безопасные вкладки, фильтры и обновление данных;
- создаётся машинный каталог видимых кнопок и полей;
- ошибки JavaScript, HTTP 5xx, screenshots и trace собираются автоматически.

Учётные данные передаются только через `EASYPI_E2E_USERNAME`,
`EASYPI_E2E_PASSWORD` и при необходимости `EASYPI_E2E_TOTP`. Файл состояния
браузерной сессии удаляется после каждого профильного запуска.

### 3. API и права доступа — слой изолированных данных готов

- получить фактическую OpenAPI-схему установленной версии;
- проверить каждый маршрут без сессии, с ролью user и с ролью admin;
- для изменяющих запросов проверить CSRF, валидацию, повтор запроса и rate limit;
- выполнять операции с файлами, пользователями и настройками только в отдельном
  namespace тестового запуска;
- после теста подтверждать удаление созданных данных.

Автоматизированы жизненные циклы временного пользователя, PiCloud и Files.
Проверяются создание, чтение, поиск, загрузка, скачивание, публичная ссылка,
ссылка с паролем и удаление. Отдельно проверяются безопасная выдача HTML/SVG,
запрет SVG-preview и границы доступа File Manager (`.env` и пути вне
`/opt/EasyPi`). Очистка выполняется и при сбое сценария.

На живом стенде этот слой обнаружил отставание установленного backend от локальных
исправлений активного содержимого. Минимальный патч PiCloud/Files установлен с
резервной копией, после чего полный профиль прошёл.

### 4. Агент — базовый live-слой готов

- создать версионируемый набор вопросов на русском, английском и немецком;
- разделить вопросы на объяснение, диагностику, действие и отказ;
- проверять подтверждение опасных действий, prompt injection и утечку секретов;
- после каждого действия сравнивать ответ агента с реальным состоянием системы;
- сохранять ожидаемые свойства ответа, а не требовать дословного совпадения текста.

Профиль `browser-agent` уже проверяет вопросы на русском и английском,
структуру и источник диагностического ответа, read-only probe, отказ неизвестному
probe, отсутствие выполнения действия с неверным confirmation token и отсутствие
явных секретов в ответе. На текущем стенде Ollama не установлен, поэтому обычный
чат проверен по корректному отказу `503`; полноценные ответы модели и немецкий
набор вопросов остаются для следующего подэтапа.

### 5. Сеть, Guard, PRISM, VPN и Chameleon

- генерировать контролируемый DNS, TCP, UDP, QUIC и HTTPS-трафик;
- сверять блокировку по DNS, точному flow PRISM и firewall-счётчикам;
- проверять внешний IP, DNS и IPv6 до, во время и после туннеля;
- отключать Wi-Fi/маршрут клиента и проверять автоматическое восстановление;
- моделировать потерю, задержку, изменение MTU и временную недоступность VPS;
- после каждого сценария проверять восстановление исходной маршрутизации.

Первый live-слой готов. Профиль `browser-network` сверяет интерфейсы, gateway,
DNS, соединения, Guard, PRISM и Chameleon. Профиль `chameleon-recovery`
перезапускает клиент, проверяет автоматическое восстановление маршрута `cham0`,
затем кратковременно блокирует только carrier к тестовому VPS и подтверждает
восстановление тем же процессом и реальную передачу контрольного пакета.
Профиль `guard-functional` берёт домен из установленного blocklist, проверяет
ответ `NXDOMAIN`, разрешение безопасного домена и совпадение фактического DNS-кода
с записью `deny` в журнале потоков.

### 6. Установка, backup и обновление

- чистая установка опубликованного архива на отдельный Pi;
- проверка отсутствия пользовательских данных и секретов в дистрибутиве;
- backup/restore SQLite и PostgreSQL с контрольными данными;
- повреждённый архив, неверная подпись, прерванное обновление и неуспешный health-check;
- проверка автоматического отката и состояния служб после перезагрузки;
- uninstall и подтверждение документированного удаления/сохранения данных.

## Критерий готовности релиза

Релиз допускается, когда обязательные локальные и live-профили зелёные, нет
необъяснённых пропусков критических сценариев, полный браузерный обход выполнен с
тестовой учётной записью, а установка и восстановление пройдены на чистом Pi.
Каждый сбой должен иметь воспроизводимый сценарий и приложенное доказательство.
